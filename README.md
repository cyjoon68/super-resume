# Super Resume

공고 맞춤 이력서, 포트폴리오, 자기소개서 워크플로우를 위한 Codex 플러그인입니다.

![Codex Plugin](https://img.shields.io/badge/Codex-Plugin-1f2937)
![Skills](https://img.shields.io/badge/Skills-Super%20Resume-2563eb)
![Version](https://img.shields.io/badge/version-v0.1.0-2563eb)

Super Resume는 이력서, 포트폴리오, GitHub 근거, 채용 공고를 읽고 구조화된 워크플로우로 안내합니다. 공고 적합도 분석, 근거 계획, 콘텐츠 수정, 경험 기반 자기소개서 작성, 프로젝트 기획서 생성, 품질 검증, PDF 출력까지 이어집니다.

경험을 나열하는 이력서가 아니라 특정 직무에 대한 적합성을 증명하는 이력서가 필요한 경우를 위해 설계했습니다.

## 빠른 시작

```bash
codex plugin marketplace add cyjoon68/super-resume --ref v0.1.0
codex plugin add super-resume@super-resume-marketplace
```

Codex를 재시작하고 호출합니다:

```
@super-resume 이 공고에 맞춰 이력서와 포트폴리오를 수정해줘.
```

경험 기반 자기소개서가 필요할 때:

```text
@super-resume 이 공고에 맞는 자기소개서를 내 이력서와 포트폴리오 근거로 작성해줘.
```

프로젝트 경험 기획이 필요할 때:

```
@super-resume 이 공고에 맞는 포트폴리오용 프로젝트 경험을 만들어줘.
```

## 작동 방식

워크플로우는 단계별 GATE로 진행되며, 다음 단계로 넘어가기 전에 사용자 확인을 받습니다. 어떤 단계든 사용자가 이전 단계로 돌아가길 원하면 돌아갈 수 있고, 중간에 종료해도 `_workspace/`의 중간 데이터는 보존됩니다.

## 작업 모드 2가지

Super Resume는 시작할 때 두 가지 모드 중 하나를 선택합니다.

### 모드 1. 이력서 기반 맞춤 (`resume_based`)

이미 이력서, 포트폴리오, GitHub 같은 경험 근거가 있을 때 사용합니다. 근거는 하나 이상 필수이며, 공고 자료를 함께 주면 그 공고에 맞춰 다시 씁니다.

흐름은 다음과 같습니다:

1. **산출물 선택** — 이력서, 포트폴리오, 자기소개서를 각각 독립적으로 선택합니다. 자기소개서를 선택하면 공고 자료나 목표 직군이 반드시 필요하고, 근거 없이 일반 자기소개서를 쓰지 않습니다.
2. **입력 수집** — 이력서 파일/텍스트/URL, 포트폴리오, GitHub 링크, 공고 URL, 프로필 사진, 지원 조건(병역, 근무 가능 시점 등), 말투를 받습니다. 말투는 전문적/자신감/간결/기술 중심/협업 중심/말투유지 중 선택하며 기본값은 원본 말투 유지입니다.
3. **분석** — 이력서를 파싱해 구조화하고, GitHub 링크가 있으면 저장소를 탐색해 경험을 보완하고, 공고에서 필수/우대 스택, 키워드, 지원 문항을 추출합니다.
4. **Fit Score** — 기술 스택 일치, 경험 연관성, 키워드 밀도, 도메인 적합도로 적합도를 계산해 먼저 보여줍니다.
5. **전략 수립** — 강조할 경험, 보강할 키워드, 재배치할 섹션을 정합니다. 자기소개서가 있으면 카테고리와 소제목, 문항 근거, 경험 근거, 섹션별 글자 수를 먼저 승인받습니다.
6. **초안 작성** — 선택한 산출물을 작성하고 v1을 보여줍니다. 피드백은 최대 3회까지 버전을 올려 반영합니다.
7. **점수 향상** — Fit Score 8.0 미만이면 약점 차원을 골라 최대 5회 반복 개선합니다.
8. **품질 검증** — 오타, 문법, 말투 일관성, 사실 일관성, 문항 충족, ATS 호환성을 검사하고 P0 이슈는 자동 수정합니다.
9. **디자인 & PDF** — 선택한 산출물 전체에 하나의 템플릿을 적용하고 산출물별 PDF를 출력합니다.

이력서만 있어도 선택한 산출물을 모두 만들 수 있고, GitHub 링크만 있어도 저장소 분석으로 경험을 추출해 작성할 수 있습니다. 피드백만 받거나 적합도 점수만 확인하는 용도로도 쓸 수 있습니다.

### 모드 2. 프로젝트 경험 기획 (`experience_blueprint`)

공고가 요구하는 경험이 없어서 새로 만들어야 할 때 사용합니다. 실제로 구현 가능한 문제해결 프로젝트 기획서를 만들고, 구현과 측정 근거까지 검증된 뒤에만 이력서 경험으로 반영합니다. 미완성 프로젝트를 완료된 경험으로 기재하지 않습니다.

흐름은 다음과 같습니다:

1. **접근 방식 선택** — 기획서의 난이도와 방향을 두 가지 중 고릅니다. 둘 다 선택할 수도 있습니다.
   - **일부러 만들 병목/제약** — 프로젝트에 의도적으로 병목을 넣고 해결 과정 자체를 경험으로 만듭니다.
     - L1 가벼운 제약: 병목 1~2개, 일반적 해결 (예: 캐시 미사용, 레이턴시 500ms 목표)
     - L2 중간 제약: 병목 3~5개, 복합적 기술 의사결정 (예: 초당 10 TPS 제한, 메모리 128MB)
     - L3 극한 제약: 병목 5개 이상, 비정형 해결 (예: DB 사용 금지, 메모리 16MB, 응답 50ms)
   - **문제 예방** — 장애를 만들기 전에 막는 설계 경험을 만듭니다. 성능, 보안, 확장성, 안정성/내결함성, 유지보수성, 데이터 무결성 중 복수 선택.
2. **접근 방식 검증** — 선택한 병목/예방이 공고와 이력서에 실제로 도움이 되는지 Relevance, Impact, Feasibility, Completeness, Gap Closure 5개 기준으로 평가합니다. 탈락하면 방식을 다시 선택합니다.
3. **기획서 생성** — 공고의 필수/우대 스택과 서비스 도메인을 분석해 프로젝트 기획서 4개를 만듭니다. 각 기획서는 프로젝트 개요와 공고 연관성, 실제 문제 상황, 비즈니스 영향, 해결 방향, 일부러 만든 병목과 해결 방법, 기술적 해결 방법, 아키텍처/데이터 플로우(mermaid), 데이터 모델(ERD), API 명세, 화면 플로우, 측정 지표, 테스트/부하테스트/관측 방법, MVP 범위, 기술 스택, 작업 분해, 완료 기준을 포함합니다.
4. **스택 일치 규칙** — 프로젝트의 주요 기술 스택은 공고 필수 스택과 70% 이상 일치해야 합니다. 공고에 없는 기술은 분석/모니터링/테스트 도구 수준에서만 씁니다.
5. **기획서 검증과 선택** — 각 기획서를 다시 5개 기준으로 검증한 뒤 요약을 보여주고, 구현할 프로젝트를 사용자가 선택합니다. 기획만 하고 종료할 수도 있습니다.
6. **구현과 해결 코드** — 선택한 기획서의 MVP 범위와 완료 기준대로 구현을 진행하고, 별도 승인 후 병목/제약 해결 코드와 부하테스트·관측·측정 코드를 추가합니다.
7. **경험 반영** — 프로젝트가 완료 기준을 충족하고 테스트/측정 근거가 확인된 경우에만 검증된 경험으로 이력서 데이터에 반영한 뒤, 선택한 산출물 작성(모드 1의 전략→작성→검증→PDF)으로 돌아갑니다. 완료 기준을 채우지 못했으면 산출물을 쓰지 않습니다.

## 레퍼런스 노트

저장소의 `references/`에는 분석, 전략, 작성 단계에서 에이전트가 사용하는 레퍼런스 노트가 있습니다:

- `core.md` — 첫 화면 요건, 실패 패턴, 지원동기 구조
- `checklist-formulas.md` — 검증 항목, 문장 패턴
- `competency-signals.md` — FE/BE 역량 신호, 문장 성숙도 단계
- `experience-blueprints.md` — 포트폴리오 프로젝트 선정 기준
- `portfolio.md` — 섹션 구조, 이력서와의 관계
- `projects.md` — STAR 구조, 수치화, 기술 깊이

각 에이전트는 자기 단계 전에 관련 레퍼런스를 읽습니다. 누락된 레퍼런스는 로그를 남기고 건너뜁니다.
